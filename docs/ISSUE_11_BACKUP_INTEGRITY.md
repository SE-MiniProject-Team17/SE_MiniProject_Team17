## Storage and backup findings

Material records are MongoDB documents containing metadata, a storage path, and a SHA-256 checksum. File bytes are stored separately in the local filesystem: `server/uploads/materials` by default or `MATERIAL_STORAGE_DIR` when configured. Accounts and material records therefore require MongoDB backup, and the referenced file objects require a coordinated file-store backup. No repository evidence establishes a daily schedule, backup scope, retention, completed backup age, or atomic coordination of those stores. There is no approved backup target or isolated restore target available here. Configuration files or this report are not proof that backups run.

No restore was attempted: without a known backup and isolated target, restoration risks overwriting data and cannot establish the 24-hour criterion. No production or shared data was touched.

## Material operation changes

The material update endpoint now accepts optional multipart file replacement as well as metadata-only JSON/PATCH. It validates the replacement before persistence, stages bytes at a new unique path, commits the new metadata, and cleans the prior file after commit. On a persistence failure the new file is cleaned and the prior record/file remain. Deletion stages the file, deletes shares and metadata, then removes the staged file; in-process failures attempt to restore the record, shares, and file. Responses identify the file checksum and metadata without disclosing its path. Upload partial-write cleanup is also covered.

These filesystem and MongoDB actions are not a single durable transaction. A process or host crash between steps can leave an orphaned/staged file or an incomplete removal; deployment-level backups and recovery remain necessary. Best-effort rollback failure also remains an operational defect requiring investigation and restoration. The tests do not claim crash consistency.

## Defects, dependencies, and next actions

1. **Backup/restore dependency (NFR-SAFE-01):** provide an approved isolated non-production environment, backup owner and schedule, MongoDB and file-store backup configuration, retention policy, and a timestamped backup no more than 24 hours old. Then restore both stores and compare account/material records and file checksums.
2. **Crash consistency (NFR-SAFE-02):** the two stores do not share a transaction. Design and approve durable reconciliation/recovery for staged/orphaned files and interrupted delete/update operations; then exercise process and network interruption in isolation.
3. **Rollback failure handling:** if compensating database or filesystem operations themselves fail, the API correctly avoids reporting success but cannot guarantee restoration. Capture sanitized operational alerting and test the recovery procedure once infrastructure is available.
4. **Related tracking:** Issue #38 operational readiness links to this report. No duplicate backup implementation was added to #38.
